# Guided parent setup rollout

This source change uses a five-minute background follow-up after recorded approval. The five-minute interval schedules a background confirmation; it does not delay successful explicit approval or setup. The confirmation asks for no reply, code or second approval. This is a staged implementation candidate, not legal certification or authorization to invite families.

## Consent decision and timing

Email verification is separate from parental approval. `give_permission` requires a verified parent email, active sign-in session, expected parent ID and affirmative guardian choice. The service submits the exact full notice to that verified inbox before approving; an unsent notice or failed submission cannot grant consent. The server derives recipient, notice hash and token. The browser cannot choose a recipient or call service-only transitions directly.

For notice v3, recorded approval permits setup/child access while a durable confirmation is pending. The confirmation repeats the original notice and withdrawal instructions. This timing and authenticated in-portal response are the proposed product design; verify their suitability for the actual COPPA email-plus method and data practices before public activation. The five-minute mail delay is an operator implementation choice, not an FTC-prescribed minimum or a compliance guarantee.

Confirmation jobs use leases and stable provider idempotency keys. Retries stop 23 hours after the first provider attempt to avoid resending beyond the provider's 24-hour idempotency window. Such jobs require operator review. Unconfirmed approvals stop permitting child access after the seven-day request expiry; they are not silently treated as delivered. Review failures/bounces promptly and let the parent withdraw/reapprove when appropriate. Successful confirmation persists with the account. Withdrawal, changed email/notice, expired rehearsal and deletion are checked at the database boundary. A late provider acknowledgement cannot restore withdrawn consent.

## Parent experience

A verified account opens a short welcome/permission step, creates a six-digit PIN, saves the first explorer and family tooth reward in one transaction, then offers Family Vault or Hand Over the Magic. Optional age/gender stay optional and hidden under optional details. PINs and unlock proofs stay in memory, never local storage. A reload asks for a PIN again where needed. Existing families with completed guide/profile/PIN skip setup when permission allows; parent review/deletion remains available without giving consent. Development preview is clearly labelled and never records fake consent.

First-explorer save is bound to the signed-in parent, an active PIN unlock and permission. A repeated request ID cannot create another explorer or overwrite reward/profile details. Setup saves no tooth entry and awards no Fairy Bucks. Finishing marks the existing guide-progress record; the long guide and FAQ remain accessible in the portal. Hand Over the Magic creates a child token, signs out locally and verifies the parent session is gone before storing the child token.

The existing signup confirmation link still targets `https://fairybucks.com/auth.html`; the valid callback now resumes setup. Existing password/PIN recovery routes are retained. No new redirect allowlist entry is needed.

## Timing and monitoring

The email becomes eligible five minutes after explicit approval. A once-per-minute database check normally submits it around five to six minutes later, plus execution/network/provider time. A three-to-seven-minute inbox arrival is a target, not a guaranteed delivery time. It never holds up successful setup. Signup verification and the initial direct notice are separate and are not deliberately delayed by this setting.

The scheduler sends only to the fixed project worker endpoint, with an empty request body and a private Vault credential. Only operational aggregates are exposed in `supabase/operators/confirmation_delivery_status.sql`; never inspect or export Vault plaintext or request Authorization headers. This job's own cron execution records are pruned after seven days; other jobs' records are untouched. pg_net responses use its default six-hour retention. A successful cron SQL invocation only means an HTTP request was queued: check the HTTP status and mail acknowledgement too. The local test harness simulates Vault, cron and networking; a real hosted schedule/delivery rehearsal remains necessary after installation.
